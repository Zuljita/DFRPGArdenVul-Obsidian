# Vault Proposal Approval Workflow

Discord-reaction-driven approval for vault edits. Runs through Hermes (REST-only,
no separate bot) and writes decisions to local JSONL files. Apply step
dispatches approved edits to the matching applier and writes to the vault.

## How a round goes

1. **Propose**: e.g. `python3 scripts/vault_automation.py propose-article-edits --limit 30` writes `data/automation/proposals/article_edit_proposals.json`.
2. **Post**: `python3 scripts/vault_proposals_discord.py post` reads the JSON, posts each unposted proposal to #botland as a markdown message, and seeds the message with three reactions: ✅ approve · ❌ reject · ⏭ skip. Idempotent — re-runs skip already-posted ids.
3. **React**: you add a reaction to each card in Discord.
4. **Poll**: Hermes cron runs `python3 scripts/vault_proposals_discord.py poll --allowed-users <YOUR_USER_ID>` every 5 minutes. For each undecided card, it reads the reactions; the first one by an allowed user wins. It records the decision and edits the original message to append "— Approved by …" so the channel shows the outcome.
5. **Apply**: when you want to flush the queue, run `python3 scripts/vault_proposals_discord.py apply --apply`. It dispatches each `approve` decision to the matching applier (currently `article_edit`), writes the edit, and marks the proposal_id consumed.

## Subcommands

```
post     [--channel-id ID] [--limit N]
         Post new proposals not already in proposal_message_index.jsonl.

poll     [--allowed-users csv] [--limit N]
         Read reactions on undecided messages; record decisions.
         Empty allowed-users = anyone in channel.

apply    [--apply]
         Dispatch decisions to appliers. Default dry-run.

status   [--show-pending]
         Counts + sample of pending proposals.
```

## Adding a new proposal kind

The `post` and `poll` halves are kind-agnostic (they just need a `proposal_id`
and basic display fields). To wire in dedup or media-ingestion proposals:

1. Add a loader in `all_proposals_indexed()` that returns the proposals
   keyed by `proposal_id` and tagged with their kind.
2. Add an `apply_<kind>(proposal, apply)` function that knows how to write
   the change to the vault, returning `("applied"|"noop"|"error", detail)`.
3. Register it in the `DISPATCH` dict.

That's it — `render_card_text` already handles common proposal field names
(article_path, target_section, proposed_text, rationale, sources, caption,
filename, etc.) for display.

## Operational gotchas

- **Token sharing with Hermes is fine** — script is REST-only (POST/GET/PUT/PATCH against discord.com/api/v10). Hermes' gateway WebSocket is untouched.
- **One vote per proposal**: first allowed-user reaction wins; changing your mind requires editing `proposal_decisions.jsonl` by hand and re-running apply.
- **Card edited after decision**: the script appends a `— Approved by …` line to the original message. If you re-poll a resolved message it's a no-op (the decision is already in the JSONL).
- **Deleted cards**: if you delete a card in Discord, `poll` errors on that message and skips. To recover, delete the matching line in `proposal_message_index.jsonl` and re-`post`.
- **Rate limits**: script paces ~0.3s between Discord calls and respects 429 retry-after. Posting 25 cards ≈ 30s.
